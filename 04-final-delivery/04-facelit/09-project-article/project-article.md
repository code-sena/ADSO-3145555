# FaceLit: gestión de asistencia académica con apoyo de reconocimiento facial
Artículo del proyecto - entrega final ADSO 3145555. Revisión documental: 5 de noviembre de 2026.
Autoras: María José Rodríguez Oyola, Valery Sinaí Trujillo Quintero y Mariana Valenzuela Penagos. SENA, Análisis y Desarrollo de Software. Instructor referenciado en el artículo recibido: José de Jesús Motta.
## Resumen
FaceLit organiza información académica y registros de asistencia mediante una aplicación con perfiles de coordinador, instructor y aprendiz. La solución documentada integra un cliente Expo/React Native, un backend Java/Spring Boot, un servicio facial Python/FastAPI y PostgreSQL con pgvector. El backend concentra autenticación, autorización y reglas del evento de asistencia; el servicio facial encapsula evaluación de captura y comparación de referencias. Este artículo presenta el problema, el desarrollo de la solución y el alcance de las evidencias disponibles. Se actualiza la topología del artículo anterior con base en la documentación reciente del repositorio. Los resultados automatizados y el funcionamiento comunicado por el equipo se distinguen de una aceptación experimental o institucional.
Palabras clave: asistencia académica; reconocimiento facial; monolito modular; FastAPI; PostgreSQL; trazabilidad.
## 1. Introducción y problema
El registro de asistencia debe vincular cada aprendiz con una ficha y una sesión de formación. La información dispersa dificulta consultar antecedentes y detectar inconsistencias. FaceLit busca reunir preparación de datos, identificación asistida, registro y consulta en un recorrido con permisos diferenciados.
El objetivo del proyecto es desarrollar una solución de gestión de asistencia con acceso por rol e integración facial. Los objetivos específicos incluyen organizar programas y fichas, autenticar usuarios, preparar sesiones, vincular referencias faciales y consultar resultados persistidos. No se dispone de línea base institucional que permita cuantificar ahorro de tiempo o reducción de errores.
Coordinación administra usuarios e información académica; el instructor trabaja con sesiones y consultas autorizadas; el aprendiz realiza enrolamiento y consulta propia. La carpeta admin representa al coordinador, sin implicar un cuarto rol implementado.

## 3. Desarrollo de la solución
El cliente Expo/React Native organiza pantallas, navegación, formularios, captura y comunicación HTTP. Hooks, stores y contextos comparten estado por responsabilidad. El backend Java 17 con Spring Boot 3.4.1 se ejecuta como monolito modular; controladores reciben solicitudes, servicios coordinan reglas y repositorios acceden a datos. El servicio Python/FastAPI separa las dependencias de visión por computador del proceso Java.
La persistencia utiliza PostgreSQL 16 con pgvector. Liquibase administra cambios de esquema y Hibernate valida la estructura al iniciar el backend. La base contiene dominios de seguridad, roles, datos académicos, ambientes, reconocimiento facial, notificaciones y aceptación legal. Java y FastAPI comparten PostgreSQL; no existe independencia de datos por servicio en la arquitectura descrita.
En el flujo facial reciente, el cliente envía la captura al backend por HTTPS. Java valida identidad, permisos y contexto, invoca FastAPI por red interna y aplica reglas de asistencia antes de confirmar el evento. La web no debe acceder a PostgreSQL ni llevar una clave privada del servicio facial.
## 4. Captura, reconocimiento y reglas
La documentación actual describe cuatro retos activos: MOVE_UP, MOVE_DOWN, MOVE_CLOSER y MOVE_AWAY. Una secuencia utiliza dos retos distintos y siete imágenes por reto. La evaluación facial y el registro del hecho de asistencia son responsabilidades diferentes.
MediaPipe aporta puntos o métricas faciales para analizar geometría y movimiento según lo descrito por el proyecto. InsightFace/ONNX Runtime participa en detección y representación facial; pgvector almacena referencias vectoriales. La malla de puntos no identifica por sí sola a una persona y una secuencia de movimiento no constituye certificación de resistencia a suplantación.
El umbral observado de 0.65 es similitud; no equivale a 65 % de precisión. El resultado necesita contexto de sesión, autorización, reglas temporales y control de duplicidad. Enrolar un rostro y registrar asistencia son operaciones distintas.
## 5. Despliegue y operación
El documento reciente de despliegue describe un VPS Hostinger, Docker Compose y Caddy. Caddy sirve la web y actúa como proxy de API y WebSocket; backend, servicio facial y PostgreSQL permanecen en red interna. Render/Vercel se conserva como propuesta histórica y no como descripción del despliegue reciente.
El reporte del 27 de octubre registra respuestas web/login 200, salud facial 200, API administrativa sin autenticación 401 y WebSocket 101; también informa 45 changesets Liquibase. Esos resultados acreditan comprobaciones técnicas reportadas de ese corte. No demuestran que el mismo código continúe desplegado ni miden disponibilidad prolongada.
Los manuales distinguen entorno local y VPS. Antes de actualizar se debe registrar versión, proteger configuración, respaldar y validar migraciones. La documentación mantiene pendiente el ensayo de restauración separado y la aceptación del APK exacto si se presenta Android.

Las 16 capturas únicas comprenden 8 de coordinación, 1 de instructor y 7 de aprendiz. Muestran gestión académica, Ambientes, consultas, preparación y validación facial, notificaciones y perfil. El formulario CSV no acredita una importación completa; los botones de exportación no sustituyen el archivo descargado; captura en validación y aviso de finalización son evidencias separadas.
El paquete de noviembre contiene ajuste local del frontend para consulta de aprendices en lotes de hasta 80 y DB local 422aac6; el informe de despliegue declara que esos ajustes se publicaron por SSH/SCP sin push a GitHub. El dominio documentado es https://facelit.tech. Una reconstrucción desde un tag remoto requiere cotejo con el manifiesto del paquete.

La separación de componentes facilita mantener la visión por computador fuera del backend Java, pero exige coordinar contratos, permisos y esquema compartido. Las mejoras reportadas incluyen cámara, persistencia del registro y traducciones. Sin medición antes/después no se cuantifica su impacto.
La evaluación pendiente debe distinguir rendimiento, exactitud de identidad, resistencia a suplantación, permisos y usabilidad. Una prueba automatizada con inferencia controlada no sustituye una evaluación biométrica con participantes autorizados, diversidad de condiciones y métricas definidas.
## 7. Conclusiones
FaceLit reúne gestión académica, acceso por rol y asistencia apoyada por procesamiento facial en una arquitectura con backend modular y servicio especializado. La documentación reciente sitúa la coordinación en Java y describe publicación web en Hostinger con servicios internos.
La entrega dispone de requisitos, diseño, manuales y evidencia de pruebas con alcances diferenciados. Para cerrar la aceptación deben relacionarse los resultados con el tag final, actualizarse los estados por requisito y conservarse evidencia reproducible. No se presentan porcentajes de precisión, disponibilidad ni ahorro sin medición.
